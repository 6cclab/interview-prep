# Web UI groundwork for voice drills

Read-only research. Source: `docs/superpowers/specs/2026-08-07-voice-drills-design.md`
(the approved voice design), every module in `voice/`, `.claude/CLAUDE.md`,
`.claude/rules/no-spoilers.md`, `package.json`. Not read: `solutions/**`,
`system-design/**/reference.md`, `patterns.md` (per hard project rule).

No design or implementation recommendations below. Where a claim is inference
rather than something read directly in code, it is flagged **[inference]**.

## 1. Reuse boundary

| Module | Web-path fate | Why |
|---|---|---|
| `context.ts` | **Move to server unchanged** | Pure file-reading + prompt assembly, `node:fs`/`node:path` only. No terminal dependency at all. This is the module the spoiler gate rests on (see §2). |
| `chunk.ts` | **Move to server unchanged** | Pure string state machine (`SentenceBuffer`), zero I/O, zero terminal dependency. Trivially portable to any JS runtime including the browser, but its job (deciding what to hand to TTS) is a server-side concern under the split described in §2/§3. |
| `transcript.ts` | **Move to server unchanged** | Pure formatting (`formatSession`, `splitTrailer`) plus `node:fs` writes to `local/`. `local/` is gitignored and lives in the repo checkout, so this must run wherever the repo checkout is — the server, not the browser. No terminal dependency. |
| `interviewer.ts` | **Move to server unchanged** | Wraps `@anthropic-ai/sdk`'s `client.messages.stream`. The API key must never reach the browser, so this has to stay server-side regardless of portability. No terminal dependency. |
| `session.ts` | **Logic reusable, shape does not survive unchanged** | `runSession`'s control flow (speak → record → transcribe → reply) is portable, but it is written as one long-lived async function holding a closure over `entries`, blocking on `deps.nextTurn()` in-process. An HTTP server has no equivalent of "the function is still on the stack waiting." See §3 — this is the one module that needs real restructuring, not a straight copy. |
| `audio.ts` | **Dead on the web path** — confirms the working assumption | `record()` spawns `ffmpeg` with `-f avfoundation`, a macOS-only capture backend, over a subprocess. `MediaRecorder` in the browser replaces its entire job (mic → encoded audio) with no use for this module's API (`Recorder.stop(): Promise<WavPath>`) or its ffmpeg dependency. Confirmed dead, not just "probably." |
| `devices.ts` | **Dead on the web path** — confirms the working assumption, but check the hidden dependency below | `listInputDevices`/`listOutputDevices` shell out to `ffmpeg -list_devices` and `say -a '?'` — both macOS/ffmpeg specific and meaningless once capture is `MediaRecorder` and playback is `SpeechSynthesis` (the browser exposes device enumeration itself, via `navigator.mediaDevices.enumerateDevices()` and `SpeechSynthesis.getVoices()`, entirely differently). Dead. **But**: `readDeviceConfig()` in this same file reads `local/voice.json` off disk — that's a server-side filesystem read, unrelated to device listing, and if anything in a future design wants a persisted user preference file, this is the only place that pattern already exists. Flagging it so it isn't lost when the file is marked dead wholesale. |
| `speech.ts` | **Mixed — does not cleanly split along "replace with browser API," check carefully** | This file has two unrelated halves: `whisperTranscriber()` (STT, shells out to a local `whisper-cli` binary — see §4, does *not* have a browser equivalent) and `saySpeaker()`/`sayArgs()` (TTS, shells out to macOS `say`, direct browser-API replacement via `SpeechSynthesis`). The working assumption bundles "the say-based Speaker" as replaced by `SpeechSynthesis` — true for `saySpeaker`, but `whisperTranscriber` lives in the same file and is untouched by that assumption; it still needs a home (server-side, unavoidably — see §4). Also note: `sayArgs`/`saySpeaker` support an explicit output-device argument (`-a <id>`) — a capability `SpeechSynthesis` does not expose (browsers pick the system default output); that's a feature loss worth naming in §5, not just a mechanical swap. |
| `cli.ts` | **Replaced wholesale — this is the terminal-dependency-carrier, not audio.ts/devices.ts** | Owns `readline/promises` for turn-yielding ("press Enter"), `process.argv` parsing, `process.exit`, `console.log`/`console.error` as the entire UI, and a `mkdtempSync`/`rmSync` scratch-dir lifecycle tied to one OS process's lifetime. None of this survives a client/server split as-is; it becomes some combination of route handlers + a browser event for "turn yielded." This is the module doing the most invisible work in the current design — it wires devices, resolves env-var overrides, and owns the try/finally that guarantees `rmSync` runs, none of which show up by reading module names alone. |

**Bottom line on the working assumption:** `audio.ts` is confirmed fully dead — it has no field that survives. `devices.ts` is fully dead *for its stated purpose* (device listing), but its config-file-read pattern (`readDeviceConfig`) is the one piece worth noting rather than discarding unread. The bigger miss in the working assumption is `cli.ts`: it, not `audio.ts`/`devices.ts`, is where the terminal-specific plumbing (readline, argv, process lifecycle, scratch-dir cleanup) actually lives, and it isn't obvious from the module name that it's the terminal-dependency-carrier — "cli.ts" sounds like a thin wrapper, but it's where turn-taking, device resolution, and process lifecycle are currently fused together.

## 2. The spoiler gate under a client/server split

**This is the highest-stakes question in this document. Read it before anything else changes.**

The design doc is explicit about the mechanism: *"context.ts owns a per-track allowlist and is the only thing in the system that opens a file for the model... The model is given no tools at all, so the spoiler files are unreachable by construction rather than by policy."* Concretely, `context.ts`:

- Owns `DENIED` (regexes for `solutions/`, `patterns.md`, `reference.md`) and `assertNoSpoilers()`, run against the allowlist *before* any read.
- Owns `allowedPaths(track, problem)` — the only function that names which files exist to be read at all.
- Owns `buildSystemPrompt()` — the only function that calls `readFileSync` on those paths and assembles the string sent to the model.
- Owns `competencyCoverage()` — the mechanism that turns "don't read the story you're about to ask for" from a prose instruction (`mock.md`) into a structural guarantee: it parses `## ` headings out of `local/stories.md` and never lets the story *bodies* into any string that leaves the function.

**What must stay server-side to preserve the guarantee:**
1. `context.ts` itself — unmodified, and specifically the fact that `buildSystemPrompt` is the *only* function anywhere that calls `readFileSync` for content destined for the model. Any second code path that reads a file into a prompt (even a "just for now" convenience one) breaks the "unreachable by construction" property back down to "unreachable by policy."
2. The repo checkout / filesystem access itself — `root` (currently `process.cwd()` in `cli.ts`) has to be a path the server process can read, and the browser must never be handed a `root`, a path, or a raw file read result to construct with.
3. `problem` slug validation (`PROBLEM_SLUG` regex in `context.ts`) — this is the thing standing between a user-supplied string and a path-traversal read. It already exists and already runs server-side implicitly; under a web split it must run on the value as it arrives from an HTTP request, which is a new (and now adversarial-shaped) input surface that `context.ts` did not have to consider when its only caller was a local CLI typed by the same person running the process.
4. The Anthropic client and API key (`interviewer.ts`'s `anthropicStream`) — obviously server-side, and reinforces point 2: nothing about assembling the request or holding the key can move to the browser.
5. `competencyCoverage()`'s heading-only parse of `local/stories.md` — the mechanism, not just the file, has to stay server-side; a browser-side "let's just fetch stories.md and extract headings in JS" would require serving the file's bytes to the browser first, which defeats the purpose even if the browser-side code is scrupulous about it.

**What would tempt an implementer to leak prompt assembly or reads to the browser**, reasoning from the current CLI flow in `cli.ts`:

- `buildSystemPrompt(root, track, problem)` is called once, synchronously, before the session starts (`cli.ts` line ~72-75), and its *string result* is threaded into `createInterviewer`. In a web split, the natural-looking move is an endpoint like `POST /session { track, problem }` that returns... what? If an implementer has the system prompt string in hand server-side and is building a "resume/inspect this session" or debug view, sending that string (or any excerpt of it) to the browser as a response body is the single biggest way this guarantee dies quietly. Nothing in the current design forces the prompt to stay server-side once assembled — it does today only because the same process that builds it also holds the only channel (the Anthropic API call) that consumes it, and a human at a terminal has no way to ask the process to print it back.
- `problem` currently arrives as `process.argv[3]`, typed by Andre himself, at a terminal he controls, running a process he started. Once `problem` arrives over HTTP, it is attacker-shaped input for the first time in this system's life — `PROBLEM_SLUG` already guards against traversal, but the *reasoning* "well, it's just Andre typing" that made the CLI feel safe stops applying, and an implementer porting the flow might not re-derive why the regex matters.
- `splitTrailer()` in `transcript.ts` strips the `story-log` fenced block from the interviewer's raw text before speech — but note `interviewer.lastRaw()` (used in `cli.ts` line 101) *does* still contain the raw trailer, unstripped. That's fine today because `lastRaw()` is called once, server-side, purely to feed `appendStoryLog`. If a web UI exposes anything like "show me the interviewer's full last response" for debugging or transcript display, `lastRaw()` is the obvious thing to reach for, and it is exactly the wrong thing to send to the browser unfiltered — it would leak the story-log block (not a spoiler-file leak, but a different kind of "internal state reaching the client" mistake in the same family).
- Nothing in `context.ts` or the spec enforces "the browser never receives file content" as a runtime check — it's true today purely because there is no code path that does it, not because something asserts against it. A web split adds the first code paths (HTTP handlers) where such a check would need to be a deliberate design decision rather than an emergent property of the architecture.

## 3. Session state and the API surface

`runSession()` (`voice/session.ts`) is a single async function that runs for the entire drill: it holds `entries: SessionOutcome` as a local variable, loops with `for (;;)`, and at each iteration calls `deps.speaker.speak()` (currently a blocking `say` subprocess call awaited in sequence per sentence), then `deps.startRecording()`, then blocks on `await deps.nextTurn()` — which in `cli.ts` is `rl.question('')`, i.e. it suspends the whole function until a human at a terminal presses Enter. There is no serialization boundary anywhere in this design: state lives on the JS call stack and in closures, for as long as the process runs.

**What breaks when that loop is split across HTTP requests:**

- **State has to move off the stack and into something addressable between requests.** HTTP is request/response; nothing holds a JS call stack open across two separate requests. `entries`, the current turn number, the interviewer's `messages` history (itself closed over inside `createInterviewer`, not exposed by its `Interviewer` interface at all — only `turn()` and `lastRaw()` are), and whichever recorder/session-scratch state exists all need an explicit session object — in memory keyed by a session id, or a store — that request N+1 can look up. This is new: `runSession` today never needs a session id because it *is* the session.
- **`SessionOutcome.endedEarly`** is set only when `interviewer.turn()`, `recorder.stop()`, or `transcriber.transcribe()` throws, and it is read by nothing shown here except implicitly — `cli.ts` doesn't branch on it, it just always writes whatever entries came back and moves on. Under a split, "the interviewer turn failed" and "the recording failed" become failures of *individual HTTP calls*, not of one long-running function — there's no single `runSession` left to catch the error and mark `endedEarly`, so that responsibility (catch a mid-turn failure, decide the session is over, still persist whatever transcript exists) has to be reconstructed at the layer that manages the stored session state, and each endpoint that can fail mid-drill needs to know how to reach it.
- **A streamed turn (today: `for await (const sentence of deps.interviewer.turn(said))`, each sentence immediately spoken) maps onto SSE or a WebSocket as "server pushes sentence-chunks as they're produced,"** which is a reasonably direct translation of the `AsyncIterable<string>` `Interviewer.turn()` already yields — that part of the design already has the right shape for streaming transport. What does *not* map directly: today, "speak sentence" (`await deps.speaker.speak(sentence)`) happens in lockstep inside the same loop that's still pulling more sentences from the model — the loop is naturally paced by TTS taking real wall-clock time. Move TTS to the browser (`SpeechSynthesis`) and the server-sent stream of sentences and the client-side act of speaking them are now two different processes with no shared clock; something has to decide whether the server paces sentence delivery to speech rate, sends everything as fast as the model produces it and lets the browser queue, or the browser controls pacing and pulls — none of that pacing decision exists in the current code because speak-and-fetch-next were the same synchronous step.
- **Browser tab closes mid-drill:** nothing in `runSession` or `SessionDeps` has a concept of "the far end disconnected." Today the "far end" is a terminal `readline` interface in the same process — if the terminal closes, the process typically dies too, and `cli.ts`'s `finally` block (`rl.close()`, `rmSync(scratch, ...)`) runs as part of normal shutdown. An HTTP/WebSocket server outliving a closed browser tab is the default, not the exception — a closed tab is a live server session with no client, holding recorder/temp-file/API-stream state, until something times it out. Nothing here designs for that; it's a genuinely open gap, not a "the design handles it, just relocated" case.
- **Where the synchronous design resists the split most concretely:** `runSession`'s single `for (;;)` loop is written under the assumption that *within one iteration*, speaking and recording-until-yielded are sequential steps it fully controls end to end — it calls `startRecording()` then immediately `await deps.nextTurn()`, and only after that resolves does it call `recorder.stop()`. There is no notion in the interface of "recording is happening; a separate signal (an HTTP call) will arrive later to end it." That's the piece requiring real re-architecture rather than a wrapper: `startRecording`/`nextTurn`/`stop` currently model one continuous foreground operation, and a web split needs at least two separable actions (start capture; later, stop capture and hand off audio) that can be invoked by two different HTTP requests with unrelated timing.

**Minimum endpoint set** — sketched from what the loop's steps are, not a recommendation on transport:
- Create a session (`track`, `problem?`) → server runs `buildSystemPrompt` + `createInterviewer`, returns a session id.
- Start a turn / stream the interviewer's reply for that session id (SSE or WS message) — server-side equivalent of `interviewer.turn(said)`.
- Submit the audio (or transcript, depending on where STT runs — see §4) for the turn just recorded, keyed by session id.
- End the session → server writes the transcript (`transcript.ts`'s `formatSession`/`writeSession`) and, for `mock`, `appendStoryLog` if a trailer was present.
- (Implied by tab-close handling being unsolved above) some way to reap or time out an orphaned session — not present in today's design at all.

## 4. Transcription in a browser world

Today: `record()` in `audio.ts` runs `ffmpeg -f avfoundation ... -ar 16000 -ac 1` — the *capture* step already produces 16kHz mono PCM wav directly, on the assumption baked into the code comment ("whisper's native input format, so no resampling step"). `whisperTranscriber()` in `speech.ts` then shells out to a local `whisper-cli` binary with `--file <wav>`, over `execFile`.

`MediaRecorder` in a browser does not produce wav at all by default — it produces an encoded container (commonly `audio/webm;codecs=opus`, browser-dependent) at whatever sample rate the input track negotiates, not 16kHz mono PCM. So the conversion whisper.cpp needs (arbitrary-rate stereo/mono webm/opus → 16kHz mono wav PCM) that today happens for free as a side effect of the `ffmpeg` capture invocation has to happen somewhere else entirely once capture moves to `MediaRecorder`.

**Where it should happen** — this is inference, not something confirmed in the codebase, since no browser-side code exists yet: whisper.cpp is a local binary (`whisperTranscriber`'s `run(opts.binary, ...)` via `execFile`) — it is not a browser-invocable thing regardless of audio format, so **[inference]** the conversion has to happen server-side, after the encoded blob crosses the network from browser to server, using something like `ffmpeg` (already a system dependency of this repo per `audio.ts`) to transcode webm/opus → 16kHz mono wav before handing the result to the unmodified `whisperTranscriber`. The alternative — decoding/resampling in the browser via Web Audio API before upload — is technically possible **[inference]** but note it would mean writing new browser-side audio code with no existing analog in `voice/` to reuse, versus reusing the ffmpeg dependency the repo already has. Either way, `whisperTranscriber()` itself is unaffected: its contract is "give me a wav path," and it stays server-side either because the browser can't run `whisper-cli` (true regardless of format) or because that's also where the transcoding step lives.

One detail worth surfacing: `whisperTranscriber`'s `--file` flag and `parseWhisperOutput`'s segment-timestamp parsing assume a *complete* wav file handed over at once — the design is turn-based batch transcription, not streaming STT (the spec's risks section explicitly names streaming STT as a possible future mitigation for latency, "at the cost of a key, per-minute billing, and sending audio off the machine" — i.e., a genuinely different STT architecture, not a tweak). A web UI does not by itself change this: whichever side does audio transcoding, the STT step remains "wait for a complete turn's audio, then transcribe it," same as today.

## 5. What genuinely gets better, and what gets worse

**Better:**
- No macOS-only dependency for capture/output (`ffmpeg -f avfoundation`, `say`) on the client side — `MediaRecorder`/`SpeechSynthesis` are cross-platform browser APIs, so the client no longer has to be a Mac. (Server-side whisper.cpp is untouched either way, so this is a client-portability win only, not an end-to-end one — the machine running the server likely still needs to be the same kind of machine that runs whisper.cpp acceptably.)
- Device selection (`voice/devices.ts`, `local/voice.json`) becomes the browser's native device picker / OS default — removes the "wrong hardcoded index silently records HDMI silence" failure mode `cli.ts` explicitly warns about (lines 78-83), because the browser mediates device selection instead of an unvalidated index into an ffmpeg device list.
- `readline`'s "press Enter" turn-yield and terminal output become ordinary UI affordances (a button, visible transcript) instead of a bare terminal loop — likely more comfortable for a 45-minute session **[inference — no data on this, purely plausible]**.

**Worse / lost, stated plainly:**
- `saySpeaker`'s `-a <audioDevice>` output-device selection (§1) has no `SpeechSynthesis` equivalent — the browser always uses the OS/browser default output device, so per-session output routing is a capability that disappears, not just relocates.
- Tab-close / connection-loss handling does not exist today and is a new problem the CLI never had (§3) — the terminal version's failure modes are captured by `endEarly` in `session.ts`; "the client vanished mid-turn with no signal" is not one of the failure modes anything currently handles.
- Latency character changes: today, TTS speaking happens synchronously in the same loop that's pulling model output (§3) — a UI that instead streams sentences over the wire and speaks them client-side introduces a new pacing/buffering problem that doesn't exist in the terminal version, purely as a consequence of moving TTS off the box that's also running the loop.

**Non-goals the spec rejected that a UI would be tempted to quietly reintroduce** — direct quotes from the spec's Non-goals section:
- *"A whiteboard for `/design`. Real design interviews involve drawing, but `rubric.md` does not grade the diagram... Adding a canvas is scope that buys no score."* A web UI is the single most natural place to add a drawing canvas "since it's a webpage now" — nothing about the rubric changed, so this temptation is worth flagging explicitly as still rejected, not reopened by the medium.
- *"Barge-in / real-time duplex. An interviewer who cuts you off is higher fidelity and materially more work, and interruption handling is not the failure mode being trained. Deferred, not rejected."* Browser STT/TTS toolchains make continuous listening and interrupt-style UX comparatively easy to reach for (many web speech demos default to that pattern) — a UI implementer reaching for a familiar "voice assistant" interaction pattern could reintroduce duplex/barge-in as an incidental side effect of picking a common browser voice-UI pattern, not as a deliberate revisit of this non-goal.
- *"Replacing the typed commands. `/mock` and `/design` stay exactly as they are. Voice is a second entry point to the same prompts, not a migration."* Not directly threatened by a web UI, but worth naming: if the web UI becomes the more polished/preferred entry point, there's a soft-migration risk (`/mock`/`/design` quietly atrophying from disuse) that is a product-attention risk rather than a code one — nothing in the code enforces "the typed path stays equally maintained."
- The turn-taking rationale — *"Let silence sit. Do not fill it. Thinking time is the exercise... A VAD threshold short enough to feel responsive will end his turn mid-thought."* — is not a listed non-goal but is argued at length in the spec's Turn-taking section as the reason continuous-record-plus-Enter beats voice-activity detection. Browser-native voice UI patterns (many `MediaRecorder` tutorials default to VAD-based auto-stop, and some browser STT setups make continuous streaming with auto-segmentation the path of least resistance) are exactly the kind of default a UI implementation could slide into without anyone deciding to reopen this — flagging it here even though it's not phrased as a "Non-goal" in the doc, because the reasoning against it is identical in shape to the rejected non-goals.

## 6. Open questions for the design conversation

No recommendations below — tradeoffs only, for the user and the other agent to resolve.

1. **Transport for the streamed turn.** SSE (simpler, one-directional, fits "server pushes sentences") vs. WebSocket (bidirectional, needed if the browser also needs to push events like "recording started/stopped" or a future barge-in). Tradeoff: SSE is less to build and reason about; WebSocket is more room to grow into if turn-taking signals need to flow both ways.

2. **Where session state lives between requests.** In-process memory (simplest, but ties the whole feature to a single server process/instance, and a server restart loses in-flight sessions) vs. an external store (survives restarts, but is new infrastructure for a personal tool). Tradeoff is operational complexity vs. resilience, for a tool whose sessions are ~45 minutes and single-user.

3. **Who paces sentence delivery to speech** — server throttles the stream to roughly speech rate, vs. sends everything immediately and the browser queues/buffers for `SpeechSynthesis` to consume at its own pace. Tradeoff: server-side pacing needs the server to estimate speech duration (fragile, voice-dependent); client-side queuing is simpler but means the "stream" is really "burst then locally paced playback," which changes what "interruptible" would even mean if barge-in is ever revisited.

4. **Audio transcoding location** — server-side ffmpeg transcode of the browser's webm/opus blob to 16kHz mono wav (reuses the ffmpeg dependency already in the repo, keeps browser code minimal) vs. browser-side resampling via Web Audio API before upload (no new server dependency beyond what's already assumed, but is new code with no existing pattern in `voice/` to extend). Tradeoff is where the new code and its failure modes live.

5. **What happens to an orphaned session on tab close** — auto-end and persist whatever transcript exists so far (mirrors today's `endEarly` philosophy of "never discard collected entries") vs. hold the session open for some grace period in case of reconnect (more forgiving of flaky connections, but requires a timeout/cleanup mechanism that doesn't exist anywhere in the current design). No existing code or spec language answers this — it's a genuinely new decision, not a port of an existing one.

6. **Whether `local/voice.json` (device config) and `local/` transcript writes stay meaningful concepts at all in a browser world**, since device selection moves to the browser's own picker and the "local" in `local/` currently means "this terminal session's machine" — if the server and the browser are ever on different machines **[inference — the spec doesn't say they must be the same machine, and nothing in the code enforces it]**, "local" stops unambiguously meaning what it means today, and that's a naming/semantics question, not just a config one.

7. **Whether STT (whisper.cpp) and TTS (browser `SpeechSynthesis`) split across two different "locality" guarantees is acceptable long-term** — audio never leaving the machine was an explicit rationale for local whisper.cpp; moving TTS to the browser doesn't violate that (browser TTS was never the privacy-sensitive direction — the mic audio is), but it's worth the design conversation explicitly re-confirming that the privacy rationale in the spec was about *input* audio, not output, since a skim of "audio.ts and speech.ts both get touched" could conflate the two.
