# Reference Design: Notification Fanout System

Spoiler. Read `rubric.md` and attempt the design in
`local/designs/notification-fanout.md` before opening this.

## 1. Requirements

**Functional**

- Ingest events from producing services (comment posted, order shipped, price
  drop, broadcast announcement).
- Resolve the audience for an event: one user (targeted) or many (mass fanout via
  a followers/segment list).
- Apply per-user, per-channel preferences and quiet hours before deciding to
  deliver.
- Deliver via push, email, SMS, in-app, through third-party providers per channel.
- Deduplicate: the same logical notification never delivered twice on the same
  channel to the same user, even under retry.
- Track delivery state per (notification, user, channel) distinctly from "sent to
  provider."

**Non-functional**

- Large fanout events (5-10M users) complete within a few minutes, not hours.
- The fanout/ingest path stays responsive even when a downstream provider is slow
  or rate-limiting — backpressure on one channel shouldn't stall others.
- At-least-once delivery is acceptable and expected; exactly-once is not required
  because idempotent consumers make at-least-once safe more cheaply.

**Non-goals**

- The in-app feed's client-side UI (pagination, read state rendering).
- Building custom push/SMS transport — third-party providers own wire-level
  delivery to devices and carriers.

## 2. Estimation

- Baseline: 20,000 events/s, average 2.5 channels/user → ~50,000 delivery
  tasks/s from targeted, single-user events. This is a manageable, steady load.
- The number that actually sizes the system: **one mass-fanout event**. 10M
  users × 2.5 channels = 25M delivery tasks generated by a single event. If the
  product requirement is "delivered within a few minutes" (say, complete audience
  resolution + task emission within 3 minutes = 180s), that's ~139,000 delivery
  tasks/second sustained *just from fanout expansion*, before a single message
  reaches a provider. This dwarfs the 50k/s steady baseline — **the system must
  be provisioned for burst fanout expansion, not average event rate.**
- Storage: event records are cheap — 20k events/s × (say) 500 bytes ≈ 10MB/s,
  trivially durable in any store, low volume relative to everything else.
  Per-user delivery-state rows are the dominant volume: a single mass event
  produces 25M rows; at a sustained 20k events/s baseline (mostly single-user)
  plus periodic mega-events, delivery-state writes are the system's actual
  throughput bottleneck, not event ingest.
- Provider throughput: FCM/APNs typically sustain on the order of low hundreds
  of thousands of pushes/second per app at reasonable scale, but with per-app
  and per-token rate limits that make a naive 139k/s unthrottled blast risky.
  This means the fanout-expansion rate (~139k/s) and the provider-delivery rate
  are two different numbers, and the design needs a buffer (a queue) between
  them so bursts in one don't become bursts in the other.

## 3. API surface

**Ingest (from internal producing services):**

```
POST /events
{
  "type": "post.published",
  "actor_id": "user_123",
  "target_ref": "post_456",
  "audience": {
    "kind": "followers_of",       // or "single_user", "segment"
    "ref": "user_123"
  },
  "priority": "normal"             // or "urgent" — affects quiet-hours override
}
-> 202 Accepted { "event_id": "evt_789" }
```

Critically, `audience` is a **reference** (follower list ID, segment ID, single
user ID), never an inline array. A 10M-entry array in a request body is both an
API design failure and a synchronous-latency failure — audience resolution
happens downstream, asynchronously, in batches.

**Provider delivery-status webhook** (inbound, from push/email/SMS providers):

```
POST /webhooks/provider-status
{ "provider": "fcm", "provider_message_id": "...", "status": "delivered"|"failed"|"bounced", "occurred_at": ... }
```

This is how "sent to provider" gets upgraded to "delivered" (or downgraded to
"failed") asynchronously, since most providers confirm delivery out-of-band from
the initial send call, not synchronously.

**Read (for in-app channel, client-facing):**

```
GET /users/{id}/notifications?cursor=...&limit=50
POST /users/{id}/notifications/{id}/ack
```

Out of scope per the prompt to design the feed UI, but the read/ack contract is
part of "getting it delivered and stored," so it's specified minimally here.

## 4. Data model

Three storage concerns with distinct volume/access patterns — treating them as
one undifferentiated "database" is the main trap in this design.

**(a) Event records** — durable, low volume (~20k/s writes of small rows).
Postgres, one row per event: `event_id, type, actor_id, target_ref, audience_ref,
created_at`. This is the source of truth for "what happened," referenced by
every downstream delivery task.

**(b) Per-user delivery state** — the dominant volume: up to 139k writes/s
during fanout bursts, 25M rows from a single mega-event. A wide-column /
partitioned KV store (DynamoDB or Cassandra) keyed by `user_id` as the
partition key and `notification_id#channel` as the sort/clustering key:

```
PK: user_id
SK: notification_id#channel
attrs: status (queued|sent|delivered|failed|bounced), provider_message_id,
       created_at, delivered_at
```

Partitioning by `user_id` gives fast "get my notifications" reads (the in-app
channel's read path) and spreads the 139k/s write burst across many partitions
instead of hammering one hot row — a relational table with row-level
transactional writes at this rate, especially if it also had to serve the
`GET /users/{id}/notifications` read path under load, is the wrong tool: it
would need either heavy sharding to match what Dynamo/Cassandra give for free,
or would become the bottleneck itself.

**(c) User preferences & quiet hours** — small (500M rows, one per user, rarely
written), read on nearly every delivery decision. Postgres as source of truth,
with an aggressive read-through cache (Redis, keyed by `user_id`, TTL a few
minutes) in front — this table is read far more than written and easily fits in
cache, so it should never be the thing throttling fanout throughput.

**Dedup mechanism**: the delivery-state table's key
(`user_id, notification_id#channel`) doubles as the idempotency key. A delivery
worker retrying a send does a conditional write ("insert if not already
`sent`/`delivered`") — a redelivered task becomes a no-op against this key
rather than a duplicate send.

## 5. Scale path

**First bottleneck: fanout expansion** — turning one event into millions of
per-user delivery tasks. Mechanism: an event lands on an `events` queue; a pool
of fanout workers consumes it, resolves `audience_ref` by paginating the
follower/segment list in batches (e.g. 1,000 user IDs per page), and for each
batch emits per-user delivery tasks onto per-channel queues (`push-tasks`,
`email-tasks`, `sms-tasks`). Worker count and queue partition count scale
roughly linearly with fanout volume — this is an embarrassingly parallel step,
the constraint is provisioning enough worker throughput and queue partitions to
sustain ~139k/s task emission during the mega-event case.

**Second, independent bottleneck: per-channel provider throughput**, which does
*not* scale by adding more fanout workers — see Failure Modes for the pacing
mechanism. This is why fanout expansion writes to a queue rather than calling
providers directly: the queue absorbs the mismatch between the ~139k/s fanout
burst rate and each provider's sustainable ingest rate.

**At 10x (500k-1.25M req/s from a 100M-user mega-event)**: fanout workers and
queue partitions scale near-linearly — add workers, add partitions, this part of
the design doesn't change shape. Provider-side pacing (token-bucket rate per
provider, see Failure Modes) becomes the dominant constraint, and the acceptable
completion-time SLA for a mega-event may need to relax (a few minutes becomes,
say, 15-30 minutes) since no single provider integration can absorb an order of
magnitude more push volume instantly regardless of internal parallelism.

**At 100x (1.25-2.5B delivery tasks, an extreme mega-event)**: synchronous
per-user fanout for every recipient stops being the right model for the in-app
channel specifically. This is the same shape as the classic social-feed
fan-out-on-write-vs-fan-out-on-read problem: precomputing a delivery-state row
for every one of 250M followers when most won't check their notifications for
hours is wasted write throughput. Switch the in-app channel (not push/email/SMS,
which are inherently push-delivered and need the task either way) to
fan-out-on-read for very-high-follower-count actors: store the event once,
resolve "does user X have unread notifications from this event" lazily when
user X opens their feed, falling back to fan-out-on-write for normal-size
audiences where precomputation is cheap and gives simpler read-path code.

## 6. Failure modes

**Push provider (APNs/FCM) down or rate-limiting:** push tolerates delay well —
queue the task and retry with exponential backoff over minutes to hours. A
token-bucket rate limiter per provider, sized to the provider's documented
sustainable rate, sits in front of the provider call at all times (not only
during errors) — this is the mechanism that prevents the 139k/s fanout burst
from being blasted at a provider that can only sustain a fraction of that,
which is the normal operating condition during any large fanout, not an edge
case.

**SMS provider down:** SMS is disproportionately used for urgent/transactional
content (verification codes, critical alerts) where users and product owners
expect near-immediate delivery. A blanket "queue and retry silently" is wrong
here — pair SMS failures with either a fallback channel (push/email if the
notification's priority is `urgent` and the user has another channel enabled)
or an operational alert if SMS delivery failure rate crosses a threshold,
since silent multi-minute SMS delays for time-sensitive content are a product
failure, not just a technical one.

**Email provider degraded:** least time-sensitive of the three — long retry
windows (hours) are acceptable and expected; email is the natural fallback
target for "eventually consistent" delivery.

**Audience/follower-list service down mid-fanout:** a fanout worker that's
partway through paginating a 10M-entry follower list and loses access to the
audience service has an explicit resume point — the pagination cursor is
checkpointed (e.g. persisted per fanout job, not held only in worker memory) so
a restarted or reassigned worker resumes from the last completed page rather
than restarting the entire fanout from zero or silently dropping the remainder.
Partial fanout (some users notified, others not, mid-failure) is a normal
transient state, not a bug — the checkpoint is what makes it recoverable rather
than permanent.

**Delivery-state store (DynamoDB/Cassandra) degraded:** this is on the write
hot path for every delivery task. Workers apply backpressure — slow down task
consumption from the per-channel queues rather than dropping delivery-state
writes — since queues can absorb backlog far more gracefully than a lossy write
path can absorb silently-missing delivery records.

## 7. Tradeoffs

**At-least-once + idempotent writes vs. exactly-once messaging infrastructure.**
Chosen: at-least-once delivery everywhere (queues redeliver on ambiguous
ack/timeout), made safe by the delivery-state table's conditional write acting
as the dedup key. Rejected exactly-once: achieving true exactly-once semantics
end-to-end (through queue, worker, and provider call) requires distributed
transactional coordination that's expensive and still doesn't fully eliminate
the problem at the provider boundary — the provider itself might receive a
duplicate call and there is no way to make a third party's API exactly-once from
the caller's side. Idempotent writes solve the actual requirement (no duplicate
*visible* notification) more cheaply and more robustly than chasing exactly-once
messaging.

**Fanout-on-write vs. fanout-on-read for the in-app channel.** Chosen:
fanout-on-write as the default (simple, fast reads), fanout-on-read as an
override for very-high-follower-count actors at extreme scale (see Scale Path,
100x case). This is a direct application of the classic social-feed fanout
tradeoff, scoped specifically to the in-app channel — push/email/SMS don't have
this option since they're inherently push-model deliveries that need a task
emitted regardless of whether the user ever "reads" a feed.

**Per-user ordering vs. global ordering.** Chosen: per-user-partitioned queues
(a given user's tasks for a given channel are processed in order relative to
each other) with no ordering guarantee *across* users. Reasoning: a user must
never see "comment deleted" processed before "comment posted" for their own
notification stream, but there's no product requirement that user A's
notifications be globally ordered relative to user B's. Enforcing global
ordering (a single strictly-ordered log) would serialize the entire fanout
pipeline behind one ordering constraint that delivers no product value and
directly conflicts with the parallelism the fanout-expansion step needs at
139k/s.

## What candidates typically get wrong here

- **Enumerating the audience inline in the event payload** instead of passing a
  reference and resolving it downstream — this alone makes the mass-fanout case
  impossible to design correctly, since a 10M-entry array can't move through a
  synchronous ingest call.
- **Designing around the 20k events/s average** and never explicitly computing
  what one mega-event costs in delivery tasks, missing that the burst — not the
  average — is what sizes the fanout-expansion and provider-pacing components.
- **"The queue handles retries" as a complete idempotency answer**, without
  naming the actual dedup key or the conditional-write mechanism that makes a
  redelivered task a no-op instead of a second notification.
- **One blanket retry/backoff policy for all three provider channels**, missing
  that push, SMS, and email have materially different urgency and failure
  tolerance, and that SMS failures in particular often need a fallback channel
  or an operational alert rather than silent queueing.
- **Treating provider rate-limiting as an outage** rather than the expected
  steady-state behavior during any real fanout burst, and therefore not
  designing continuous pacing (token bucket per provider) as a first-class,
  always-on component rather than an error-triggered retry path.
- **Missing the fan-out-on-write vs fan-out-on-read tradeoff for the in-app
  channel** even after having reasoned through an equivalent social-feed problem
  elsewhere — the pattern doesn't transfer automatically just because the
  candidate has seen it before in a different framing.
